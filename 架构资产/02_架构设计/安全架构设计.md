## 1. 文档概述

### 1.1 编制目的

本文档对五角色 AI 助理系统进行系统性安全架构设计，基于 STRIDE 威胁建模方法论，全面识别系统在欺骗（Spoofing）、篡改（Tampering）、抵赖（Repudiation）、信息泄露（Information Disclosure）、拒绝服务（Denial of Service）、权限提升（Elevation of Privilege）六个维度的安全威胁，并针对每类威胁制定缓解措施。同时，本文档从认证授权、数据安全、审计合规、纵深防御四个层面设计安全控制体系，确保系统在 macOS 本地优先部署架构下的机密性、完整性和可用性。

### 1.2 系统安全上下文

本系统为基于飞书 Bot 统一交互的本地优先 AI 助理系统，部署于 macOS Apple Silicon 单机环境。核心安全特征如下：

| 安全维度 | 当前状态 | 风险评估 |
|----------|----------|----------|
| 网络暴露面 | cloudflared 隧道将 Flask :5101 和 File Bot :5102 暴露至公网 | 严重 — 隧道无 IP 白名单/Token 验证 |
| Webhook 认证 | callback_server.py 仅检查 challenge 字段，无签名验证 | 严重 — 任意攻击者可伪造请求 |
| 凭证存储 | 飞书凭证存于 .env（APP_ID/APP_SECRET），已纳入 .gitignore | 中等 — 本地隔离，但无加密 |
| API 密钥存储 | settings.yaml 中 6 个 API Key 明文存储 | 主要 — 已纳入 .gitignore，但本地明文 |
| 数据加密 | 对话历史使用 Fernet 对称加密，密钥存于 .crypto_key | 中等 — 加密已实现，密钥管理待完善 |
| 文件访问控制 | whitelist.yaml 按助手配置路径白名单，security.py 校验 | 良好 — 已实现路径隔离与敏感目录过滤 |
| 权限边界 | 全程用户权限运行，无 sudo，sys-assistant 待补建 | 良好 — 最小权限原则已贯彻 |
| 云端数据出境 | free-api-hub 云端路由将对话数据发送至外部服务 | 主要 — 需合规评估 |
| 审计日志 | 需求要求保留 180 天，security_audit 台账待建立 | 中等 — 待实施 |

### 1.3 安全设计原则

| 原则 | 说明 | 在本系统的应用 |
|------|------|---------------|
| 最小权限原则 | 每个组件仅授予完成功能所需的最小权限 | 五角色助手按 whitelist.yaml 限制文件访问；sys-assistant 白名单命令；全程无 sudo |
| 纵深防御原则 | 多层安全控制，单层失效不致系统沦陷 | 网络层（隧道）+ 应用层（认证/校验）+ 数据层（加密）+ 运维层（监控/备份）四层防御 |
| 安全默认值原则 | 默认配置即为最安全配置 | 路径默认拒绝（DEFAULT_ALLOWED_PATHS 仅项目目录）；敏感目录默认拒绝 |
| 攻击面最小化原则 | 减少暴露给攻击者的入口和功能 | 飞书 Bot 为唯一交互入口；/health 仅返回状态；无管理后台 |
| 失败安全原则 | 安全控制失败时系统应进入安全状态 | 路径校验失败返回拒绝；推理后端失败降级而非暴露错误详情 |

### 1.4 术语定义

| 术语 | 定义 |
|------|------|
| STRIDE | 微软威胁建模框架，涵盖 Spoofing/Tampering/Repudiation/Information Disclosure/Denial of Service/Elevation of Privilege 六类威胁 |
| Fernet | Python cryptography 库提供的对称加密方案，基于 AES-128-CBC + HMAC-SHA256 |
| RBAC | 基于角色的访问控制（Role-Based Access Control） |
| tenant_access_token | 飞书企业级访问令牌，通过 APP_ID + APP_SECRET 换取，有效期 2 小时 |
| cloudflared tunnel | Cloudflare 提供的隧道服务，将本地端口安全暴露至公网，自动 HTTPS |
| .crypto_key | Fernet 加密密钥文件，存储于项目根目录，权限 0o600 |

## 3. STRIDE 威胁建模

本节是安全架构的核心。针对系统的六类 STRIDE 威胁，逐一分析威胁描述、攻击面、风险等级、缓解措施和当前状态。

### 3.1 S — Spoofing（欺骗）

欺骗威胁指攻击者伪装成合法身份访问系统资源。

| 威胁类型 | 威胁描述 | 攻击面 | 风险等级 | 缓解措施 | 状态 |
|----------|----------|--------|:--------:|----------|:----:|
| 伪造飞书 Webhook 请求 | 攻击者向 `/webhook` 端点发送伪造的飞书事件 JSON，冒充飞书平台触发消息处理流程，可能导致未经授权的命令执行或数据访问 | cloudflared 隧道公网 URL → Flask :5101 `/webhook`、`/webhook_chat`、`/webhook_file`、`/webhook_sys` | 严重 | 1. 实现飞书事件签名验证：使用 `X-Lark-Signature` 头 + `Encrypt Key` 对请求体进行 HMAC-SHA256 签名校验；2. [待规划] 隧道层增加 IP 白名单（仅允许飞书开放平台 IP 段）；3. [待规划] 增加 Token 验证中间件，拒绝无有效签名的请求 | 待实现 |
| 隧道无认证访问 | cloudflared 隧道将 Flask 服务暴露至公网，当前无任何访问控制，任意互联网用户可直接访问 `/webhook`、`/health` 端点 | cloudflared 隧道公网 URL（https://xxx.trycloudflare.com） | 严重 | 1. [待规划] 配置 cloudflared Access 策略，要求飞书 IP 段或预共享 Token；2. [待规划] 在 Flask 层增加来源 IP 校验中间件；3. 收紧本地监听地址为 127.0.0.1（cloudflared 转发不受影响） | 待规划 |
| 伪造飞书用户身份 | 攻击者获取合法飞书用户的 open_id 后，通过伪造 Webhook 冒充该用户发送命令，触发文件操作或系统管理命令 | Webhook 事件中的 `sender.sender_id.open_id` 字段 | 高 | 1. Webhook 签名验证（同上）确保事件来源可信；2. [待实施] 建立用户白名单（allowed_open_ids），仅授权用户可执行管理命令；3. sys-assistant 命令白名单限制可执行操作 | 待实现 |
| 伪造飞书 API 调用 | 攻击者获取 APP_ID/APP_SECRET 后冒充系统调用飞书 API，读取/发送消息、下载用户文件 | .env 文件中的 FEISHU_APP_ID / FEISHU_APP_SECRET | 高 | 1. .env 已纳入 .gitignore，不提交版本控制；2. .env 文件权限收紧为 0o600；3. [待实施] 定期轮换 APP_SECRET；4. 飞书开放平台配置 IP 白名单限制 API 调用来源 | 部分实现 |
| 伪造推理后端响应 | 攻击者中间人篡改 free-api-hub 云端路由的响应，注入恶意内容到 AI 回复中 | Flask → free-api-hub 的 HTTPS 出站连接 | 中等 | 1. free-api-hub 使用 HTTPS 传输，TLS 防止中间人；2. [待规划] 增加推理后端响应校验（内容长度限制、敏感关键词过滤）；3. 降级至本地推理避免云端依赖 | 部分实现 |

### 3.2 T — Tampering（篡改）

篡改威胁指攻击者未经授权修改数据或系统配置。

| 威胁类型 | 威胁描述 | 攻击面 | 风险等级 | 缓解措施 | 状态 |
|----------|----------|--------|:--------:|----------|:----:|
| 对话历史篡改 | 攻击者直接修改 `data/chat_history/` 下的加密对话历史文件，注入恶意上下文影响 AI 行为，或删除历史破坏对话连续性 | 本地文件系统 data/chat_history/ 目录 | 中等 | 1. 对话历史已使用 Fernet 加密（AES-128-CBC + HMAC-SHA256），HMAC 确保完整性，篡改后解密会抛出 InvalidToken 异常；2. [待实施] 增加文件哈希校验日志，定期比对；3. daily_backup.sh 每日备份提供恢复能力 | 已实现 |
| 配置文件篡改 | 攻击者修改 settings.yaml（后端配置）、whitelist.yaml（路径白名单）等配置文件，改变系统行为或扩大文件访问范围 | config/settings.yaml、config/whitelist.yaml | 高 | 1. settings.yaml 已纳入 .gitignore（版本控制不追踪变更，但本地可改）；2. [待实施] 配置文件增加完整性校验（启动时计算 SHA256 并与记录比对）；3. [待实施] 配置文件权限收紧为 0o600；4. 审计日志记录配置变更 | 部分实现 |
| 消息内容传输篡改 | 攻击者在飞书→隧道→Flask 传输链路中篡改消息内容，修改用户命令或注入恶意指令 | 飞书开放平台 → cloudflared → Flask 的 HTTPS 传输链路 | 中等 | 1. cloudflared 隧道提供端到端 HTTPS（TLS 1.3），防止传输层篡改；2. [待实现] 飞书 Webhook 签名验证确保消息体完整性；3. HTTPS 证书由 Cloudflare 自动管理 | 部分实现 |
| 白名单路径绕过篡改 | 攻击者通过符号链接、路径穿越（../）等手段绕过 whitelist.yaml 和 security.py 的路径校验，访问白名单外的文件 | file-assistant 文件操作命令的路径参数 | 高 | 1. security.py 已实现路径规范化（resolve_path 使用 os.path.abspath）；2. 已实现符号链接外部指向检测（is_symlink_outside）；3. 已实现敏感目录过滤（SENSITIVE_PATTERNS 含 /etc、/var、.ssh 等）；4. [待实施] 增加 realpath 二次校验防止 TOCTOU 竞态 | 已实现 |
| 推理后端响应篡改 | 攻击者篡改 free-api-hub 云端路由返回的推理结果，注入恶意指令或误导性内容 | Flask → free-api-hub HTTPS 连接 | 中等 | 1. HTTPS 传输防止中间人篡改；2. [待规划] 对推理响应增加内容审计（记录但不阻断）；3. clean_reply() 已清理部分指令残留前缀；4. 降级至本地推理可消除此风险 | 部分实现 |
| 加密密钥篡改 | 攻击者替换 .crypto_key 文件，导致后续加密数据使用攻击者控制的密钥，或使已有数据无法解密 | .crypto_key 文件（项目根目录） | 高 | 1. .crypto_key 已纳入 .gitignore；2. 密钥文件权限已设为 0o600；3. [待实施] 密钥文件增加备份与完整性校验；4. daily_backup.sh 当前排除 .crypto_key（需评估备份策略） | 部分实现 |

### 3.3 R — Repudiation（抵赖）

抵赖威胁指用户或管理员否认曾执行某项操作，系统缺乏不可篡改的审计证据。

| 威胁类型 | 威胁描述 | 攻击面 | 风险等级 | 缓解措施 | 状态 |
|----------|----------|--------|:--------:|----------|:----:|
| 用户否认发送消息 | 用户否认曾通过飞书发送特定命令（如文件删除、系统管理操作），系统缺乏带身份标识的操作审计记录 | 飞书消息事件（im.message.receive_v1）中的 open_id 与消息内容 | 中等 | 1. [待实施] 建立操作审计日志，记录每条消息的 open_id、消息内容摘要、时间戳、处理结果；2. 审计日志写入独立文件，权限 0o600；3. 审计日志保留 180 天 | 待实施 |
| 管理员否认执行系统命令 | 通过 sys-assistant 执行的服务启停、进程终止、备份还原等操作，操作者事后否认 | sys-assistant 命令执行（#5/#sys 前缀路由） | 高 | 1. [待实施] sys-assistant 所有命令执行记录审计日志（操作者 open_id、命令内容、执行结果、时间戳）；2. 审计日志写入 security_audit 台账；3. 审计日志不可篡改（追加写入模式） | 待实施 |

### 4.1 飞书 Webhook 认证（签名验证 — 待实现）

#### 4.1.1 当前状态

当前 `callback_server.py` 的 `webhook()` 函数仅检查请求体中是否包含 `challenge` 字段（飞书 URL 验证机制），对实际事件请求**无任何身份验证**。任意攻击者只需知道隧道公网 URL 即可发送伪造的飞书事件 JSON 触发消息处理流程。

```python
# 当前实现（无认证）— callback_server.py L65-74
@app.route("/webhook", methods=["POST"])
def webhook():
    data = request.get_json()
    if not data:
        return jsonify({"code": 400, "msg": "empty body"}), 400
    if "challenge" in data:
        return jsonify({"challenge": data["challenge"]})
    threading.Thread(target=handle_event, args=(data,)).start()
    return jsonify({"code": 0, "msg": "success"}), 200
```

#### 4.1.2 目标设计

实现飞书事件订阅 v2.0 的签名验证机制：

                           ┌─────────────────────┐

                           │ 3. 提取 X-Lark-     │
